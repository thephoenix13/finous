B2C PWA — Build Plan

How the Finous prototype becomes the production PWA. Scope is Phase 1 and Phase 2 of the Screen Inventory. This plan builds on Architecture v1.1 and treats Prototype v2 (Daylight) as the visual and behavioural reference. Dated 27 Oct 2026.

2Scope and phasing

  • In scope now (P1 + P2): onboarding and auth, Day 0 tools, error, offline and skeleton states, home and detail screens, AI Advisor, voice agent, settings, privacy and consent management.
  • Later (P3 to P5): loan suite, health score, marketplace, goals, investment hub, premium. Prototype v2 already designs most of these, so they become reference rather than new design.
  • Ship order: P1 first. It needs no Account Aggregator and no licence.

4PWA specifics

  • Manifest: standalone display, 192 and 512 icons plus a maskable icon, theme colour and language set.
  • Per-tenant manifest: white-labelling means each subdomain needs its own name, icons and theme colour. The gateway serves the manifest dynamically from the resolved tenant.
  • Service worker: precaches HTML, JS, CSS and icons only. Navigation falls back to the offline screen. Nothing financial is ever cached.
  • Updates: prompt the user ("New version available") instead of updating silently.
  • Install: the Android install prompt, plus manual Add to Home Screen steps for iOS.
  • Session: access token held in memory, refresh token in an httpOnly cookie, silent refresh at app start.
  • Biometric lock: WebAuthn platform authenticator (Screen 11.5).
  • Push alerts: Web Push. iOS supports it only for installed PWAs, so it ships with the alerts milestone, not before.
  • Logout: clears every cache and in-memory state.
  • No background sync: deliberate, because the data is financial.

6Quality gates

  • Shared finance module: the prototype's loan maths (EMI, months to close, prepay, refinance) moves into a tested finance module. The numbers audit from the prototype becomes unit tests, so figures cannot drift apart between screens.
  • Single source for figures: screens read derived values, never hard-coded text, as in the prototype's F object.
  • Accessibility: WCAG AA, axe in CI, keyboard and screen-reader pass per milestone. Prototype v2 already sets the patterns: focusable rows, labelled controls, reduced-motion, 44px targets.
  • Performance and PWA: Lighthouse PWA and performance budget enforced in CI.
  • End to end: one Playwright flow per prototype journey.

8Risks and open items

  • Regulatory lead times: Setu (AA) and Aadhaar eKYC approvals gate M3. The mock API keeps everything else moving.
  • Advice boundary: the Advisor and recommendation screens must stay information, not advice. Have a SEBI-aware reviewer approve the final copy, including voice, which shares the same guardrails.
  • iOS push: limited to installed PWAs, so alerts need an in-app fallback.
  • Voice latency: it depends on the Deepgram to Finous LLM callback.
  • Hindi copy: needs proper translation, not machine output, for financial terms.
  • Data residency: all data services must run in Azure Central India. The static shell on a Vercel CDN holds no user data.
  • Multi-tenant theming: per-tenant manifest and runtime tokens are not in the prototype and need design time in M1.

9First steps

  • Scaffold Finous/app/ (Vite, React, TypeScript, Tailwind 4, vite-plugin-pwa).
  • Port the Daylight tokens and the shared components: hero card, row, card, tag, switch, slider, field, toast, tab bar, nav bar.
  • Extract the loan maths into finance with unit tests.
  • Stand up the mock API from the prototype persona.
  • Wire CI and Vercel previews, then ship the offline screen as the first PWA proof.
